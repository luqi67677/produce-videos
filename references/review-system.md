# 确认包、短回复与审批账本

## 一次只交付一个确认包

确认包是一次用户决策，不等于一个内部文件。每次等待确认前说明：

1. 本包包含哪些项目；
2. 每项当前状态和可修改内容；
3. 推荐回复格式；
4. 通过后进入哪一步。

紧密相关、低风险且能一起看懂的项目可以合并；下载/安装授权、敏感素材、授权疑点和无法回滚的外部操作必须单独询问。等待期间可以运行不依赖用户选择的只读检查，不能提前生成会被该选择推翻的下游产物。

默认确认包：

- `content-direction`：完整口播、真实素材联系表、三套风格；
- `voice`：同文案试听与最终声音；
- `production-blueprint`：素材在全量静态分镜中的实际用法；
- `final-preview`：完整低清预览和联系表。

启动信息只有缺项时出现；`high-risk` 根据隐私、授权、安装或新运动语法拆包。

## 先保证能看见或听见

- 文本：在消息中完整展示，不能只给路径。
- 图片：直接展示总览图；原尺寸文件作为补充。
- 三套风格：主入口是完整 A/B/C 总览图，三个 270×360 缩略图兜底；HTML 只能辅助。
- 音频：直接展示可播放试听，使用同一文案并清楚编号。
- 视频：直接展示可播放文件，并附联系表；播放器 HTML 不能作为唯一入口。

用户说“打不开、只看到一部分、不能播放”时暂停当前确认，换成可直接查看的产物后重新展示；不要求用户排查浏览器，也不把这类回复记为审批。

## 解释短回复

`通过`、`继续`、`可以`和“基本上可以”仅在上一条只有一个确认包、已经列清包内范围和确认后果时，才能批准整个包。

包内有多个编号或选择时使用结构化回复，例如：

> 内容和素材通过，风格 B，声音 2。

单独的 `B` 或 `2` 只批准能被唯一解释的候选，不自动批准包内其他项目。回复包含否定、修改意见或未决问题时，先处理反馈，不得擅自记为通过。

## V2 审批账本

新项目从 `assets/approval-ledger-template.json` 建立 `approval-ledger.json`。账本保留五个机器阶段：

- `script`
- `source-assets`
- `assets`
- `storyboard`
- `motion`

一个确认包可以写入多个阶段记录。例如 `content-direction` 可写入 `script` 与 `source-assets`，`production-blueprint` 可写入 `assets` 与 `storyboard`。每条记录必须：

- 写入同一个真实 `review_package` 和包含当前阶段的 `package_scope`；
- 保存用户看到的总问题、原话、解释方式和批准时间；
- 用自己的 `review_delivery` 指向本阶段主审查产物；
- 在 `reviewed_files` 覆盖本阶段实际使用文件及 SHA-256。

同包记录可以共享用户回复，但不能共享一份与阶段无关的文件来冒充覆盖。逐阶段运行：

```bash
python3 scripts/validate_review_approval.py project/approval-ledger.json \
  --require-stage <阶段> --require-approved
```

`motion` 的主产物必须是实际视频，联系表必须进入 `reviewed_files`。风格选择继续写入 `visual-style-options.json`，声音选择写入 `voice-selection.json`；账本不替代这两份专用契约。

V1.0/V1.1 独立审批文件只用于旧项目兼容；新项目不再创建五份分散审批文件。
