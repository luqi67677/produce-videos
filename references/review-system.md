# 审查交付与短回复

## 一次只确认一个阶段

每次等待用户确认前，只保留一个当前阶段，并明确三件事：

1. 现在审查的产物是什么；
2. 用户可以直接回复什么，或指出哪些修改；
3. 通过后将进入哪一步。

等待期间不提前生成下一阶段。收到回复后，先落盘审批文件并运行 `validate_review_approval.py`，通过后再继续。

## 先保证能看见或听见

- 文本：在消息中完整展示，不能只给文件路径。
- 图片：直接展示总览图；原尺寸文件作为补充。
- 三套风格：主入口是包含完整 A/B/C 的实际图片，三个 270×360 缩略图作兜底；本地 HTML 只能辅助。
- 音频：直接展示可播放试听，三条使用同一文案并清楚编号。
- 视频：直接展示可播放文件，并附 24 帧联系表；播放器 HTML 不能作为唯一入口。

如果用户说“打不开、只看到一部分、不能播放”，当前阶段立即停止。先换成可直接查看的产物并重新展示，不要求用户调整浏览器、缩放或本机权限，也不把无法查看时的回复记为审批。

## 解释短回复

`A/B/C`、编号、`通过`、`继续`、`可以`和“基本上可以”可以作为有效回复，但必须同时满足：

- 紧邻上一条消息只有一个待确认问题；
- 上一条已经写清阶段、候选编号和确认后的下一步；
- 用户回复没有同时包含否定、修改意见或新的未决问题。

若存在多个问题、多个编号体系，或回复是“嗯、看看、先这样、不确定”，不得猜测，继续完成不依赖该选择的工作；确实无法继续时只问一句澄清问题。

## 审批记录

新项目从 `assets/review-approval-template.json` 建立 V1.1 审批文件：

- `review_prompt`：用户回复前看到的单一确认问题；
- `approval_message`：用户原话；
- `approval_interpretation`：`explicit` 或 `contextual-stage-response`；
- `accepted_response_rule`：为什么这个短回复能唯一映射到当前阶段；
- `review_delivery`：主审查产物、媒体类型、是否直接展示和兜底产物。

`motion` 阶段的主产物必须是实际视频，`fallback_path` 必须是联系表，并且二者都要进入 `reviewed_files`。V1.0 审批只为旧项目兼容；新项目不得继续手写旧结构。
