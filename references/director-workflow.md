# 导演与事实工作流

## 先问四个问题

1. 谁在什么场景下遇到什么困难？
2. 现有方式为什么不够？
3. 这项技术改变了哪一个关键动作？
4. 最后给人的是什么可用结果？

回答不能只是“效率更高”“更智能”。要写成可视化的变化，例如“从逐段排查到获得可复核位置”。

## 事实分级

- **已证实**：原始资料、官方文档、实测报告或用户明确授权支持。可出现在旁白和画面中。
- **可合理演示**：用于说明机制的示意动画，不宣称为真实客户或实测结果。
- **禁止宣称**：资料缺失、容易构成误导、会导致安全/法律风险或需要客户授权。

所有数字必须有单位、工况、对象和来源。“本装置雨噪抬升”不能改写为“系统不受暴雨影响”。

## 展会 60 秒叙事

| 时间 | 任务 | 画面证据 |
| --- | --- | --- |
| 0—2 秒 | 品牌或事件钩子 | 标志、公司名或一个正在发生的异常 |
| 2—10 秒 | 问题 | 现场、人物、对象和危害机制 |
| 10—18 秒 | 阻力 | 噪声、距离、复杂工况或人工流程 |
| 18—30 秒 | 技术介入 | 产品在场景中的真实角色和机制 |
| 30—42 秒 | 技术证据 | 关键参数、实验、对比或可复核输出 |
| 42—54 秒 | 结果 | 从输出到人的确认、决策或处置 |
| 54—60 秒 | 品牌收束 | 价值句、标志和公司全称 |

不强行把一分钟填满旁白。音乐和场景需要呼吸，但画面不能因此变成无信息的空白底图。

## 打动人的边界

- 把痛点拍成可理解的因果，不用灾难镜头恐吓人。
- 把技术拍成“改变了什么”，不把抽象线条当成技术本身。
- 把参数放回工况，不用孤立大数字冒充价值。
- 把人放在结果端，不编造系统自动做完人的处置。
